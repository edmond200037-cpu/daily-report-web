# ADR-007：工項位置狀態與日報輸出群組

## 狀態

已接受，可進入分期實作。

## 背景

本次調整要同時解決兩件事：工項位置欄位長期占用畫面，以及一般施工內容被不必要地換行與編號。既有資料模型以 `TradeSection` 表示一張「工種＋廠商」施工卡；每張卡保存單一廠商、人數與多筆工項。獨立進料則以 `connectedTradeSectionId` 連到其中一張施工卡。

規劃書提出的輸出層級是「工種 → 多個廠商 → 多個工項」，並要求同工種的多廠商共同形成一個施工填報群組。這與目前以施工卡作為進料連接目標的模型存在語意落差。

## 已確認方向

- 施工內容是工項的主要資料；起始樓層、結束樓層與位置文字完全選填。
- 施工工項透過上方「工項輸入器」確認加入；未按加入的文字只屬目前操作階段，不建立 `WorkItem`。
- 展開或收起位置編輯器只是 UI 狀態，不是儲存邊界，也不應單獨造成 dirty。
- 每個工項各自組合位置與施工內容；同一廠商的有效工項以 `、` 合併。
- 沒有連結獨立進料時，一個有效廠商採單行格式，多個有效廠商分行且不編號。
- 只要輸出工種群組存在至少一筆連結獨立進料，就進入編號模式；所有施工廠商共同屬於第 1 項，每筆進料各自取得後續編號。
- 位置 UI 收斂不得改變工項拖曳、記憶、草稿／定稿、備份或進料資料的所有權。

## 決策：末尾地點不是獨立位置

- 整組位置資料完全選填；沒有任何位置仍是有效施工工項。
- 初始地點、位置文字可各自存在。
- 末尾地點代表範圍終點；只要末尾地點有值，就必須同時具有有效初始地點。
- 保留現行 validator 的「結束樓層有值時，請填寫起始樓層」規則。
- 摘要與日報 formatter 不需要定義「只有末尾地點」或「末尾地點＋位置文字」的輸出形式。

## 決策：起訖欄位維持樓層領域

- `startFloorRaw` 與 `endFloorRaw` 仍表示起始樓層與結束樓層，不改為任意地點文字。
- UI 標籤使用「起始樓層／結束樓層」，避免「初始地點／末尾地點」暗示可輸入任意區域名稱。
- 保留既有樓層正規化與格式驗證；本次不新增欄位、不移除 `startFloorNormalized`／`endFloorNormalized`，也不做 schema migration。
- `locationTextSnapshot` 繼續承擔自由文字位置，例如 A 區、北側或開挖面。

## 決策：全清空於失焦後收合

- 使用者刪除最後一個位置字元時，不立即破壞焦點或重繪工項。
- 當位置編輯區內最後一個仍有焦點的欄位失焦，且起始樓層、結束樓層、位置文字皆為空時，才自動收合該位置編輯區。
- 收合後移除位置摘要並恢復 `＋位置`。
- 若焦點只是由位置編輯區的一欄移到另一欄，不得在欄位切換途中收合；判斷必須以整個位置編輯區的 `focusout` 結果為準。

## 決策：位置資料異動使完成狀態失效

- 已完成施工卡的起始樓層、結束樓層或位置文字真正改變時，該卡立即退回草稿。
- 寫入值與原值相同時，不算資料異動，不應改變時間戳、觸發存檔或退回草稿。
- 單純點擊 `＋位置`、位置摘要、展開、收合或在位置欄位間移動焦點，不影響施工卡狀態。
- 退回草稿後，該卡及其連結進料依混合狀態預覽規則暫時不輸出，直到使用者重新完成施工卡。

## 決策：所有施工輸出異動使完成狀態失效

- 廠商、施工人數、施工內容、起始樓層、結束樓層、位置文字與工項備註，只要實際值改變，都使所屬已完成施工卡退回草稿。
- 新增、刪除或重新排序工項同樣會改變輸出，亦須使所屬已完成施工卡退回草稿。
- 共用 mutation workflow 必須先比較新舊值，再決定是否更新 `updatedAt`、排程儲存及呼叫 `markDraft()`。
- UI 狀態操作不得經過資料 mutation workflow；`toggle()`／位置展開狀態應維持純記憶體狀態，不更新日報資料的 `updatedAt`。

## 決策：工項備註保留於正式輸出

- 備註屬於單一工項，不提升為廠商或工種層級資訊。
- 有備註時，以全形分號接在施工內容後：`施工內容；備註`。
- 沒有備註時不得留下分號或空白。
- 同廠商多工項仍以 `、` 分隔；每個工項必須先完成自己的「位置＋施工內容＋備註」組合，再參與合併。

## 決策：備註採獨立按需展開

- 備註 textarea 不再永久占據每筆工項的固定高度。
- 無備註時，在工項操作區顯示輕量 `＋備註`；不得使用大型主要按鈕或另占固定一列。
- 點擊 `＋備註` 才在該工項下方展開備註編輯器。
- 有備註時移除 `＋備註`，改顯示弱化且可點擊的備註摘要，作為重新進入編輯的入口。
- 清空備註後，採與位置相同的失焦收合原則：離開備註編輯器後移除摘要並恢復 `＋備註`。
- 新增此呈現不改變既有 `WorkItem.note`、草稿儲存、定稿快照或備份格式。

## 決策：全頁最多一個工項輔助編輯器

UI 狀態採單一互斥選擇：

```ts
type ActiveWorkAuxEditor =
  | { workItemId: string; kind: 'location' | 'note' }
  | null;
```

- 點擊任何工項的 `＋位置`、位置摘要、`＋備註` 或備註摘要時，先收起目前輔助編輯器，再展開新目標。
- 同一工項的位置與備註也不得同時展開。
- 切換不跳確認視窗；欄位變更已透過日報草稿 workflow 保存，UI 收合不是提交或放棄邊界。
- 不把展開狀態寫入 `DailyReportV3`、IndexedDB、定稿快照或備份。

## 決策：施工卡收合清除輔助編輯器狀態

- 外層施工卡由展開切換為收合時，若目前輔助編輯器屬於該卡的工項，將 `activeWorkAuxEditor` 設為 `null`。
- 再次展開施工卡時，只呈現緊湊工項列與既有位置／備註摘要，不自動恢復編輯器。
- 此操作不清除位置或備註資料、不影響 dirty，也不觸發額外儲存。
- 切換日報頁籤、刪除所屬工項或刪除施工卡時，同樣清除已失去可見目標的輔助編輯器狀態。

## 決策：所有尺寸共用單一工項操作選單

- 桌面與手機皆只顯示一個具 accessible name 的工項操作入口；點擊後開啟包含「位置」、「備註」與「刪除工項」的輕量選單。
- 工項操作入口的可見符號固定使用 `⋯`，觸控範圍不得小於 44px，accessible name 使用「工項操作」；不得沿用會暗示純新增行為的 `＋`。
- 選擇項目後關閉選單，並透過同一 `activeWorkAuxEditor` workflow 展開對應編輯器。
- 操作選單是暫時 UI 狀態，不寫入日報資料，也不造成 dirty。
- 「刪除工項」必須維持危險操作語意與既有確認流程，不得因收進選單而略過確認。

## 決策：位置與備註共用摘要列

- 工項第一列維持施工內容與 utility 操作；第二列集中呈現已有的輔助資料摘要。
- 輔助資料摘要的左側必須對齊施工內容輸入框左側，不得從工項容器或拖曳控制欄起算。
- 位置與備註皆存在時，同列依序顯示 `位置：…` 與 `備註：…`，不得增加成第三層固定列。
- 兩個摘要區段各自是獨立操作入口：位置摘要開啟位置編輯器，備註摘要開啟備註編輯器。
- 只有其中一種資料時只顯示對應摘要，不保留另一段空位或分隔符號。
- 窄螢幕可對各摘要使用省略號，但必須保留可辨識標籤、accessible name 與完整內容提示。

## 決策：工項採低密度容器與單列操作入口

- 工程條目中的每筆工項以極淡底色與小圓角區分，不再以每筆固定分隔線切割；容器之間只保留必要留白，避免新增多筆工項時產生過密的水平線。
- 工項主列由左至右固定為拖曳控制、施工內容輸入、單一工項操作入口；各控制必須與施工內容輸入框的垂直中線對齊。
- 無位置或備註摘要時，工項容器不得為操作再建立第二列；既有摘要仍維持摘要列作為重新開啟入口。
- 工項操作入口與上方「加入」按鈕在所有尺寸共用固定 `44px × 44px` 尾端操作欄，使施工內容輸入框右側固定對齊工項輸入器搜尋欄右側。
- 本決策只改變呈現與操作配置，不新增持久欄位，也不改變位置／備註輔助編輯器的互斥、收合與 dirty 邊界。

## 決策：工項輸入器與重複位置限制

- 施工工項區上方提供 `輸入工項` 與 `加入`；可從同一工種的共用工項記憶選取建議，但必須按加入或有效 Enter 才建立 `WorkItem`，並保留 IME 組字期間不誤送的行為。
- 加入後輸入器清空並維持焦點；各施工卡的未加入文字只在目前操作階段分開保留，重新整理後不保存。
- 工項建議只在輸入器具有非空白搜尋文字時顯示；成功加入後必須隨文字清空一併收合，不得以空白查詢顯示常用項目並遮住下方已加入工項。
- 已加入工項仍維持拖曳、可編輯施工內容、位置、備註與刪除；不再為每筆工項顯示重複的可見「工項」標題，改用 `輸入工項` placeholder 與依目前順序產生的 accessible name。
- 同一施工卡內，相同正規化工項文字與相同正規化樓層範圍／位置文字不得重複；不同工項可使用相同位置，備註不構成區分條件。既有空白工項不得靜默刪除。
- 位置整體仍是選填；但相同工項再次加入時，若位置仍空白或與既有工項相同，系統必須立即在列內提示並阻止完成。新增後優先展開位置編輯器，讓使用者補上不同位置。
- 重複判定沿用既有 `normalizeName()`、樓層正規化與位置組合，不新增第二套正規化規則。
- 工項輸入器在所有支援尺寸皆維持搜尋欄與 `44px × 44px`「加入」按鈕同列，不在 `<=360px` 改為上下排列或將加入按鈕撐滿整列。

## 決策：工項排序只採滑鼠／觸控拖曳

- 每筆工項提供左側拖曳把手，使用者可在同一施工卡內拖曳調整順序；拖曳不得觸發施工內容輸入或外層施工卡的展開／收合。
- 不提供上移／下移按鈕、鍵盤排序或其他非拖曳替代操作；介面接受鍵盤使用者無法調整工項順序的可及性限制，以換取較低的操作密度。
- 成功排序後須重新連續編號 `WorkItem.sortOrder`，並透過共用施工輸出 mutation workflow 使已完成施工卡退回草稿；排序失敗時必須恢復原順序並提示使用者。
- 工項排序僅限該施工卡的 `workItems`，不得改變施工卡排序、進料關聯、記憶資料或定稿快照。

## 決策：位置採緊湊輸出文法

正式日報不輸出 `位置：`、括號、`｜`、破折號或額外空格。位置片段與施工內容直接串接：

| 位置資料 | 正式輸出片段 |
| --- | --- |
| 只有初始地點 | `B2F第五層支撐施作` |
| 初始＋末尾 | `B2F～B1F第五層支撐施作` |
| 只有位置文字 | `A區第五層支撐施作` |
| 初始＋位置文字 | `B2FA區第五層支撐施作` |
| 初始＋末尾＋位置文字 | `B2F～B1FA區第五層支撐施作` |

`｜`只用於 UI 位置摘要，不進入正式日報。每個可選片段都必須條件式加入，空欄位不得留下 `～` 或其他殘留符號。

## 決策：進料關聯屬於指定施工卡

目前多張 `TradeSection` 可具有相同 `tradeTypeId`，但獨立進料只連到單一 `TradeSection.id`。本次保留這項關聯語意：

- 進料關聯的擁有者是指定的 `TradeSection`，不提升為 `tradeTypeId` 層級的永久關聯。
- 刪除被連接的施工卡時，進料依既有規則解除連接；即使同工種仍有其他廠商卡，也不自動轉接。
- 在被連接施工卡仍存在時，formatter 可以把它與相同輸出工種群組的其他廠商一起呈現；這只是輸出聚合，不改變關聯所有權。
- 不新增自動轉接，也不把進料複製到其他施工卡。

## 決策：進料關聯異動不撤銷施工完成

- 完成狀態只代表施工卡的廠商、人數、工項與工項位置／備註已確認；獨立進料是外部記錄，以 `connectedTradeSectionId` 參照該施工卡。
- 新增後連接、改接、解除連接、復原解除，以及轉為普通進料時的解除連接，都必須保留所有既有施工卡的 `status`。
- 關聯異動仍須保存，並立即影響預覽與定稿的未連結獨立進料驗證；它不可呼叫 `markDraft()`。
- 施工卡自身的輸出資料實際變更時，仍維持既有規則退回草稿。

## 決策：輸出工種群組的聚合鍵

- 兩張施工卡具有相同且非空的 `tradeTypeId` 時，屬於同一輸出工種群組。
- 兩張施工卡的非空 `tradeTypeId` 不同時，即使 `tradeNameSnapshot` 相同也不得合併。
- 舊資料兩張施工卡都缺少 `tradeTypeId` 時，以標準化後完全相同的 `tradeNameSnapshot` 作為相容性聚合鍵。
- 一張有 `tradeTypeId`、另一張沒有時不得只因名稱相同而合併，避免把無法證明的舊資料關係視為確定關係。
- 此規則只負責 formatter 聚合，不改寫歷史草稿或定稿資料。

概念鍵可表示為：

```text
tradeTypeId 存在 → id:{tradeTypeId}
tradeTypeId 缺少 → legacy-name:{normalizeName(tradeNameSnapshot)}
```

## 決策：群組標題取最前施工卡快照

- 相同 `tradeTypeId` 的施工卡即使 `tradeNameSnapshot` 不一致，仍依穩定 ID 聚合。
- 群組標題使用 `sortOrder` 最前施工卡的 `tradeNameSnapshot`。
- UI 顯示名稱快照不一致警告，但不阻止完成或定稿。
- formatter 不查詢目前工種主檔，也不以主檔名稱覆寫草稿快照。
- 不一致名稱不造成自動資料修復；使用者若要統一，必須透過既有編輯流程明確修改。

## 決策：純進料不構成可定稿工種

現行 `validateTrade()` 要求廠商、施工人數與至少一筆施工工項。本次保留這項完成邊界：

- 只有連結獨立進料、沒有有效施工廠商時，不得完成或定稿。
- 必須先有廠商、有效施工人數與至少一筆非空白施工內容，連結進料才會隨該施工卡輸出。
- 原規劃書決策表中的「有效施工廠商 0、獨立進料 1+」案例，以及純進料輸出案例，不納入實作與驗收。
- formatter 不得用進料替代施工卡有效性驗證。

## 修正後的輸出矩陣

| 有效施工廠商 | 連結獨立進料 | 結果 |
| ---: | ---: | --- |
| 0 | 任意 | 不構成可定稿輸出；連結進料不能繞過施工驗證 |
| 1 | 0 | 工種與廠商同一行，不編號 |
| 2+ | 0 | 工種獨立一行，各廠商分行，不編號 |
| 1 | 1+ | 工種獨立一行，施工群組為 `1.`，進料由 `2.` 開始 |
| 2+ | 1+ | 工種獨立一行，多廠商共同屬於 `1.`，進料接續編號 |

## 決策：獨立進料必須連接，普通進料除外

- `entryType === 'independent'` 的進料只有在 `connectedTradeSectionId` 指向有效施工卡時，才可進入正式日報。
- 未連結獨立進料不得以頂層進料形式輸出，也不得被 formatter 當成普通進料。
- `entryType === 'normal'` 的普通進料不需要連接施工卡，維持既有頂層進料輸出。
- 連結獨立進料只隨其擁有施工卡輸出；施工卡若為草稿，依混合狀態規則暫不出現在預覽。
- 工種卡被刪除後，原連結進料會解除並成為待處理的未連結獨立進料，不會自動降級為普通進料。

## 決策：未連結獨立進料是阻擋定稿的中間態

- 新建獨立進料仍採既有 workflow：先儲存原始記錄，再由接線盤連接施工卡。
- 儲存成功後可以短暫處於未連結狀態，介面必須明確顯示待處理警告。
- 只要存在任一未連結獨立進料，`validateDailyForFinalization()` 必須阻止整份日報定稿。
- 預覽不得輸出未連結獨立進料；連接有效施工卡後才解除該筆阻擋。
- 不要求建立進料時同步選工種，也不為此重做進料建立表單。

## 決策：群組內進料依施工卡排序

- 先依輸出工種群組內各 `TradeSection.sortOrder` 排列廠商施工卡。
- 先輸出較前施工卡所連結的所有有效獨立進料，再輸出後方施工卡所連結的進料。
- 同一施工卡連結多筆進料時，再依進料本身的 `sortOrder` 排列。
- 不使用進料頁的全域順序跨越施工卡所有權，也不把進料插入廠商施工文字之間；所有施工廠商仍共同屬於第 `1.` 項。

概念排序鍵為：

```text
(ownerTradeSection.sortOrder, material.sortOrder)
```

## 決策：工種群組位置取最前施工卡

- 將所有施工卡依 `TradeSection.sortOrder` 排列後，以第一次遇到某聚合鍵的位置作為該輸出工種群組的位置。
- 後方具有相同聚合鍵的施工卡加入既有群組，不重複輸出工種標題。
- 同工種施工卡不必相鄰，也不新增完成或定稿驗證。
- 群組內廠商順序仍依各施工卡自己的 `sortOrder`。
- 拖曳群組內非首張施工卡只改變群組內廠商順序；只有最前成員的位置跨越其他群組時，才會改變整個群組的輸出位置。

## 決策：混合狀態預覽只採已完成施工卡

- formatter 建立預覽群組前，先只保留 `status === 'complete'` 的施工卡。
- 同工種仍為草稿的施工卡、其施工內容及其連結進料都不進入當下預覽。
- 已完成施工卡仍可正常預覽，不因同工種存在草稿卡而隱藏整組。
- 介面必須保留草稿數量警告，且存在任何草稿施工卡時禁止定稿與正式複製。
- 所有施工卡完成後，formatter 重新聚合完整工種群組。

## 決策：空白工項阻止完成

- 施工卡至少要有一筆非空白施工內容。
- 只要 `workItems` 中仍存在施工內容為空白的項目，該施工卡就不能完成。
- 使用者必須填寫或明確刪除空白工項；完成動作不得自動刪除，formatter 也不得靜默忽略。
- 位置或備註有值但施工內容空白，仍屬無效工項，不能藉由位置或備註通過驗證。

## 決策：同工種禁止重複廠商施工卡

- 同一輸出工種群組內，一個廠商只能有一張可完成的施工卡。
- 草稿編輯期間可以暫時存在重複廠商卡，但完成與定稿驗證必須阻止重複狀態。
- 系統不得自動合併重複卡片的工數、工項或連結進料；使用者必須自行整理並刪除多餘卡片。
- 「同廠商多工項以 `、` 合併」正式限定為單一合法廠商施工卡內的工項合併。
- formatter 不應把重複卡片靜默合併成看似合法的單一廠商行。

## 決策：重複廠商身分鍵

- 同一輸出工種群組內，兩張施工卡具有相同且非空的 `vendorId` 時，判定為重複廠商。
- 兩張施工卡的非空 `vendorId` 不同時，即使 `vendorNameSnapshot` 相同也不判定為重複。
- 舊資料兩張施工卡都缺少 `vendorId` 時，以標準化後完全相同的 `vendorNameSnapshot` 判定重複。
- 一張有 `vendorId`、另一張沒有時，不因名稱相同自動判定為重複。

概念鍵為：

```text
vendorId 存在 → id:{vendorId}
vendorId 缺少 → legacy-name:{normalizeName(vendorNameSnapshot)}
```

## 決策：重複廠商衝突不隱藏或自動修復

- 載入舊資料時若同一輸出工種群組存在兩張已完成的重複廠商卡，預覽保留兩條廠商施工內容。
- UI 同時顯示明確的重複廠商衝突警告；定稿驗證必須失敗。
- formatter 不自動合併工數、工項或進料，不隱藏整個工種，也不在載入時把資料改回草稿。
- 使用者整理並刪除多餘施工卡後，衝突解除，預覽回到合法的單廠商行。

## 決策：官方日報模板升為版本 2

- 將 `DAILY_TEMPLATE_VERSION` 由 `1` 提升為 `2`。
- 新 formatter 規則只用於新預覽與新定稿；既有 `FinalizedDailyReport.outputText` 不重新計算。
- 既有版本 1 定稿快照保留原文字、`templateVersion` 與 `finalizedAt`，不進行資料 migration。
- 歷史畫面與複製功能直接使用快照內的 `outputText`，不得用目前 formatter 重建舊日報。

## 待補測試契約

- 同工種兩個廠商、無進料。
- 同工種兩個廠商、進料連到第一張廠商卡。
- 同工種兩個廠商、進料連到第二張廠商卡。
- 刪除被連接的廠商卡後，同工種仍有另一張廠商卡。
- 兩張同名工種卡缺少 `tradeTypeId`。
- 沒有有效施工廠商但存在未連結進料時，定稿驗證必須失敗。

## 實作 Workflow

### Phase 1：純 UI 狀態與工項列收斂

1. 新增單一 `activeWorkAuxEditor` 與窄螢幕新增選單狀態。
2. 重構工項列為低密度容器、對齊主操作列、共用輔助摘要列、按需位置／備註編輯器。
3. 實作切換、外層收合、頁籤切換、刪除與全清空失焦規則。
4. 確保 UI 狀態不經 `daily.update()`，不改 `updatedAt` 或 IndexedDB。

### Phase 2：施工資料 mutation 契約

1. 建立共用施工輸出資料更新入口，先比較新舊值。
2. 實際異動才更新時間、排程儲存並將已完成卡退回草稿。
3. 套用廠商、工數、工項內容、位置、備註及工項新增／刪除／排序。
4. 保留樓層正規化、末尾依賴初始與空白工項阻擋規則。

### Phase 3：正規化輸出模型

```text
完成施工卡
→ 建立輸出工種聚合鍵
→ 依首次出現位置建立群組
→ 依施工卡順序建立廠商行
→ 每個工項組合位置＋內容＋備註
→ 依擁有施工卡順序取得連結進料
→ 選擇一般模式或編號模式
→ 組合模板版本 2 文字
```

### Phase 4：跨卡與定稿驗證

1. 驗證同工種重複廠商身分鍵。
2. 未連結獨立進料阻止定稿；普通進料維持頂層輸出。
3. 衝突預覽保留原資料並顯示警告，不自動修復。
4. 混合完成狀態只預覽已完成卡及其連結進料。

### Phase 5：版本與回歸

1. `DAILY_TEMPLATE_VERSION = 2`。
2. 保證版本 1 定稿快照不重算。
3. 回歸工項拖曳、工項記憶、進料接線、刪除復原、草稿儲存、預覽、定稿、歷史與備份。

## 模組邊界

- `src/main.ts`：UI render、事件轉譯與 transient state。
- `src/daily/daily-controller.ts`：施工輸出資料 mutation、狀態失效與儲存排程。
- `src/daily/daily-validator.ts`：單卡、跨卡與整份定稿不變量。
- `src/daily/daily-formatter.ts`：正規化輸出模型與版本 2 文字，不修復資料。
- `src/domain/daily.ts`：不新增持久欄位，只提升模板版本。
- `tests/unit`：分離 UI contract、validator matrix、formatter matrix 與歷史快照回歸。

## 非目標維持

- 不變更 IndexedDB schema、備份格式或定稿資料模型。
- 不自動合併或轉接工種、廠商、工項與進料。
- 不把未連結獨立進料自動轉為普通進料。
- 不重新格式化既有歷史日報。
