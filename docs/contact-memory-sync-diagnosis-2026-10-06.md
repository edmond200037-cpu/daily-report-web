# 聯絡事項記憶與線上同步診斷

## 本機修正

`contactTaskMemoryText` 統一供輸入套用記憶與定稿蒐集使用。除了預定日期及附加欄位，現在也排除工項文字內明確標示的數量／規格、常見數字加單位、尺寸、直徑及混凝土強度。原始 `ContactTask.content` 與日報輸出保留完整內容。未標示的任意型號或中文數量無法可靠推斷，應填入「數量／規格（選填）」欄位；不會自動改寫或刪除既有記憶。

## 線上觀察

2026-10-06，於 GitHub Pages 的共用工地頁面直接讀取：

- 33 筆待同步：21 筆已停止重試、11 筆衝突、1 筆待同步。
- 21 筆停止重試保存的錯誤是 `PGRST202`，找不到 `public.apply_memory_application(p_base_revision, p_entry, p_mutation_id, p_site_id)`。建立時間為 10 月 4 日，不能據此斷言資料庫現在仍未修復。
- 展開一筆 10 月 6 日的工項衝突「反力座植筋」，保留了本機已確認資料，但雲端內容是空物件。這不是可直接採用雲端覆蓋的普通文字差異。
- 程式會將逐筆記憶 RPC 回傳的版本衝突保留在 outbox；SQL 存在「同 ID 雲端資料不存在、但本機基準版本不為 0」回傳衝突的分支。這是該筆的可能原因，尚未取得正式資料庫查詢證據，不能推廣到全部 11 筆。
- Supabase `execute_sql` 唯讀函式查詢被工具核准機制拒絕：工作階段核准政策為 never。未修改正式資料庫、未重送線上操作、未選擇衝突版本。

## 修復順序

1. 先查正式資料庫是否存在記憶套用與逐筆修改 RPC，參數名稱是否一致、schema cache 是否已載入。
2. 若缺少，審查現有 `supabase/repairs/restore-memory-application.sql` 後套用並驗證；不可把套用事件任意改呼叫一般修改 RPC，避免破壞用量去重。
3. 確認函式恢復後，使用共用工地頁的「修復後重試」重新排送缺少 RPC 的停止項目。
4. 下載衝突備份，核對雲端實際 ID、父工種、版本與同名資料；逐筆建立新的解決操作。未成功前保留來源，雲端空值不得盲目覆盖本機工項。

## 驗證邊界

TypeScript、單元測試與兩種 BASE_PATH 建置驗證本機修改。一般 Vitest 受 Windows EPERM 阻擋，改用既有 artifacts 設定的 preserveSymlinks 驗證；建置同樣使用既有替代設定。不代表 GitHub Pages 已部署、手機輸入已驗收或正式同步已修復。
